PROJECT MANAGEMENT SYSTEM - PRESENTATION SCRIPT
Runtime: ~22 minutes
Delivery cues in [brackets]; everything else is spoken word.

-------------------------------------------------------------------------------
1. OPENING - WHAT THIS ACTUALLY IS                                  (90 seconds)
-------------------------------------------------------------------------------

Good morning. What I'm going to walk you through is the Project Management
System - the platform that runs the entire final-year project lifecycle for the
AIML department, from the day a student forms a team to the day their grade is
published.

I want to be precise about the scale, because "a project portal" undersells it.
This is FOUR separate web portals, backed by FOUR independent API services,
sitting on ONE shared Postgres database. Across those services there are 313
HTTP endpoints - 114 in the student API, 98 in the mentor API, 58 in the admin
API, 43 in the panel API. The database carries 25 core tables in the base
schema, and the admin service alone is authorised to operate on 37.

So this is not one app with four logins. It's four applications with genuinely
different users, different threat models, and different jobs - deliberately
kept apart.


-------------------------------------------------------------------------------
2. WHY FOUR SERVICES AND NOT ONE                                    (2 minutes)
-------------------------------------------------------------------------------

[This is the architectural thesis. Slow down here.]

The obvious question is: why not build one backend? A monolith would have been
faster to write.

Three reasons, and they're all about blast radius.

FIRST - the four user populations are not equally trusted. Students are the
largest group and the least trusted; they're the ones with an incentive to see
another team's marks. Panel members are external evaluators who need a narrow
slice of functionality during a two-hour evaluation window and nothing else.
Admin is the coordinator with god powers. Keeping those in separate processes
means a flaw in the student API cannot reach admin functionality, because that
code isn't loaded in that process.

SECOND - they have genuinely different lifecycles. The panel API is quiet for
weeks and then serves every evaluator in the department simultaneously on
presentation day. The student API is under continuous load during team
formation. Separating them means we can scale and restart them independently.

THIRD - different auth models. And this is the interesting one. The admin portal
authenticates through Supabase Auth - the coordinator signs in with
sign_in_with_password, and Supabase issues the session. The student, mentor, and
panel APIs each mint their own JWTs using python-jose, HS256, with a bearer
scheme, refresh-token rotation, and a revoked_tokens blacklist so logout
actually revokes. Those are two different security architectures living side by
side, which is far cleaner to reason about in separate services than tangled in
one.

Everything is orchestrated with Docker Compose: backends on ports 8000 through
8003, frontends on 3000 through 3003, each frontend served by its own nginx
container that also reverse-proxies /api to its backend. In production they're
four subdomains - admin, student, mentor, and panel dot glapms dot in.


-------------------------------------------------------------------------------
3. THE TECHNOLOGY - WHAT, WHY, WHERE                                (5 minutes)
-------------------------------------------------------------------------------

[Work through the four layers. Don't rush the "why" - that's the part people
remember.]

THE FRONTEND LAYER

Every one of the five frontends - the four portals plus the public landing site
- is React with Vite. Vite for the build because the dev server starts in
milliseconds and the production bundle is Rollup-optimised; with five apps in
one repo, slow builds would compound five times over.

Styling is Tailwind CSS throughout, via the official Vite plugin. The reason is
consistency across five codebases: when four people are working on four portals,
a shared utility vocabulary keeps them looking like one product without a
component library to maintain.

Framer Motion handles animation, Lucide provides the icon set, and Lenis gives
smooth scrolling - those three appear in all five apps, which is what makes the
portals feel like siblings rather than strangers.

Then the divergence, and each one is a deliberate fit to the job:

  - The ADMIN portal carries xlsx, papaparse, jspdf and jspdf-autotable -
    because admin is where data comes in and reports go out. Roster uploads
    arrive as Excel, results leave as PDF.
  - The MENTOR portal carries chart.js and recharts - mentors need progress
    visualisation across their assigned teams.
  - The PANEL portal carries recharts and jspdf - it generates the evaluation
    submission receipt.
  - The STUDENT portal carries recharts for its results and GitHub analysis
    views.
  - The PUBLIC LANDING SITE carries GSAP, because that's the marketing surface
    and it's the only place where elaborate motion is worth the payload.

THE BACKEND LAYER

All four services are FastAPI on Uvicorn, Python 3.11. FastAPI for three
concrete reasons: native async - which matters because these services spend most
of their time waiting on Postgres and on outbound HTTP; Pydantic request
validation, so malformed input is rejected at the boundary rather than deep in a
handler; and automatic OpenAPI docs.

Data access splits in an interesting way. The student and mentor APIs use
SQLAlchemy async with asyncpg, with Alembic for migrations - the full ORM,
because those services have complex relational models with team memberships,
evaluations, and milestones. The admin and panel APIs mostly go through the
Supabase Python client against PostgREST. That's a pragmatic split: admin does a
lot of broad, generic table operations where an ORM adds ceremony without value.

Around that core:

  - passlib with bcrypt for password hashing - bcrypt because it's deliberately
    slow and salted per hash.
  - python-jose for JWT signing and verification.
  - pandas and openpyxl for the Excel ingestion path - the coordinator uploads a
    spreadsheet of 500 students and it's parsed in memory, never written to disk.
  - python-docx and pypdf for document extraction - that's how problem
    statements are imported from Word documents.
  - RapidFuzz and Jellyfish for fuzzy string matching. This is a real problem
    worth naming: student names arrive from three different sources with three
    different spellings, and exact matching fails. Jellyfish gives phonetic
    matching, RapidFuzz gives fast edit-distance.
  - httpx as the async HTTP client for every outbound call.

INTEGRATIONS

OpenAI appears in six modules - problem-statement enrichment, domain
classification, and blueprint generation. Twilio for voice and SMS reminders
ahead of presentations. Google Calendar, via the official Python client, for
scheduling. And email through both fastapi-mail and raw smtplib with MIME
multipart, because some flows need attachments.

INFRASTRUCTURE

Supabase-hosted Postgres as the single source of truth. Docker Compose for
orchestration. nginx per frontend. And GitHub Actions for delivery - one
workflow builds and deploys the four-portal stack to EC2 over SSH with a
docker compose build and recreate; a second, separate workflow ships the public
landing site on Node 22. They're separate because the marketing site changes far
more often than the platform, and shouldn't require a full stack redeploy.


-------------------------------------------------------------------------------
4. THE DATABASE                                                     (3 minutes)
-------------------------------------------------------------------------------

[Frame it as one shared spine, not four databases.]

One Postgres instance, on Supabase, shared by all four services. That's a
deliberate choice - the alternative, a database per service, would mean the
panel API couldn't see the team a student belongs to without a network call, and
the consistency problems would be worse than the coupling.

The schema is organised in roughly six clusters.

IDENTITY AND COHORT. students, mentors, panels, sub_admins, and semester_config.
semester_config is the keystone - almost every other table carries a
semester_id, and it's what lets the platform run multiple batches concurrently
without them contaminating each other. Third-year and fourth-year cohorts
coexist in the same tables, separated by that column.

TEAM FORMATION. teams_validation is the authoritative team record, holding
members as a JSONB array. Alongside it, unassigned_students tracks who hasn't
joined a team, and team_join_requests carries the invitations.

PROJECT SELECTION. problem_statements holds the department's catalogue, tagged
Hardware or Software. proposals holds custom submissions from teams who want
their own topic. project_locked_ps and project_override_logs handle contention -
when two teams want the same statement.

MENTORSHIP. mentor_allocations and panel_mentors.

ASSESSMENT. This is the largest cluster: schedule_slots, evaluation_queue,
evaluation_feed, evaluation_drafts, results, absent_students, makeup_slots. And
a dedicated set of seven tables for presentation cycles - cycles, submissions,
evaluations, schedule, audit, rubrics, and evaluation scores - added by
migration, which models the fact that a semester has multiple graded
presentation rounds each with its own rubric.

GOVERNANCE AND COMMUNICATION. governance_audit records privileged actions.
communication_history and communication_templates back the mail system.
deadlines drives the reminder schedulers.

Two things worth calling out. Row Level Security is enabled on the sensitive
tables at the Postgres level - that's defence in depth beneath the application's
own checks. And the schema evolves through numbered SQL migrations in the
database/ directory, each one carrying a comment explaining the failure it fixes
- so the schema documents its own history.

MASTER DATA: ONE ROSTER THE PLATFORM TRUSTS

[Slide: the master data hub. Slow down here - this is where the data model and
the access rules meet.]

A student comes into existence in exactly one place. The students table is the
master record, and everything else in the platform treats it as the answer to a
single question: is this a real student in this cohort?

Its primary key is the university roll number - the id column is the roll number
itself, as text. That one decision is what makes the roster idempotent. Every
write is an upsert on that key, and rows are collapsed on it before they even
reach the database, so re-importing last week's sheet corrects records instead
of doubling them. Import the same file five times in any order and you still get
one record per student.

Two things write into it. The bulk importer, which resolves column headers by
alias with a substring fallback, fills anything missing from the active
semester's own defaults rather than dropping the row, and splits the sheet on
team number. And the Student Master Data screen, for adding or correcting one
student at a time.

Then look at what reads it. A password signup is rejected outright if the e-mail
isn't already on the roster - the error code is literally
STUDENT_NOT_PRE_REGISTERED, and the student is told to contact their
coordinator. Google sign-in doesn't go through that endpoint, so there's a
second gate that runs the same check over Supabase REST before letting an OAuth
session through. Every authenticated request re-checks that the token's e-mail
still resolves to a row. And the team and unassigned-student lists are derived
from it, then kept in sync - correcting a name on the master record rewrites the
member entry inside the teams_validation JSONB array and the matching
unassigned_students row, so the copies can't drift.

That's the point worth landing. Access control here isn't a separate list of who
is allowed in. It's the roster itself. Remove a student from master data and
they stop being able to sign up, stop being able to sign in with Google, and
their existing sessions stop working on the next request.


-------------------------------------------------------------------------------
5. THE FOUR PORTALS                                                 (7 minutes)
-------------------------------------------------------------------------------

[This is the functional core. Roughly 90 seconds each.]

THE ADMIN PORTAL - 25 SCREENS

This is the control plane, and the largest surface in the system.

The semester begins in Semester Settings, where the coordinator defines the
active cohort. Then Student Upload ingests the roster from Excel - parsed with
pandas, matched with the fuzzy-matching stack I mentioned. Team Validation is
where the coordinator reviews formed teams, resolves incomplete ones, and moves
students between them.

Project Allocation manages the problem-statement catalogue and assigns projects
to teams, including bulk allocation and conflict resolution. Mentor Allocation -
I'll come back to that, it's the most technically interesting screen in the
product.

For assessment: Presentation Cycles defines the graded rounds, Schedule places
teams into evaluation slots, Evaluations monitors them live, Results computes
and publishes final marks, and Absent Students handles make-ups.

For oversight: Governance carries platform deadlines and the data-freeze control
- a switch that locks the entire platform against mutation once grading closes.
Analysis and Repo Analysis give aggregate views. Views is the cross-cutting
reporting screen.

And for communication: Communication and Per-Team Mail, backed by a mail-merge
engine with named audience segments - all students, team leaders, unassigned
students, incomplete teams, teams without mentors, all mentors, or one specific
team - and templates with merge fields for team name, project title, leader, and
mentor.

THE STUDENT PORTAL - 19 SCREENS

The student journey runs left to right through this portal.

They sign up - and as of the current release, signup requires email
confirmation, so an account only activates once the person holding the mailbox
clicks the link. Then Team Proposal for forming a team and submitting a project
idea; Preferences for ranking problem statements from the catalogue, filtered by
domain and by Hardware or Software.

Once the project is underway: Milestones for staged submissions, GitHub Analysis
and GitHub Report - the platform pulls the team's repository and reports commit
distribution and per-contributor activity, which is how individual contribution
inside a team gets measured objectively. Presentations shows their scheduled
slots. Extra Activities lets them submit certificates for additional credit.
Evaluations, Results, Feedback, Mentor, Notifications, and Profile round it out.

THE MENTOR PORTAL - 14 SCREENS

It starts at sign-up, and the sign-up screen is doing more work than it looks
like. A mentor creates their faculty profile, and then picks the domains they
can supervise from a searchable catalogue - and the order they pick them in is
their preference rank. That ranking is the input the allocation engine reads
later, so onboarding and matching are the same act. Nothing has to be collected
from mentors a second time.

Assigned Teams and Detailed Team View are the mentor's home. Milestones Manager
is where they review submissions. Mentor Evaluation Form is where they score.

Two screens are the differentiators. Progress Intelligence aggregates a mentor's
teams into a comparative view of who's on track. And Alerts surfaces teams that
have gone quiet - no commits, missed milestones - so a mentor supervising eight
teams learns which one needs attention without checking all eight.

GitHub Analyzer gives the mentor the same repository intelligence the student
sees, but across their whole portfolio.

THE PANEL PORTAL - 11 SCREENS

The narrowest and most disciplined portal, because it's used under time pressure
with an audience watching.

Slot Management and Slot Team List show the day's queue. Evaluation Parameters
exposes the rubric - which is built dynamically per team from the presentation
cycle's configuration, not hardcoded.

Time-Bound Evaluation is the centrepiece. Each evaluation session runs against a
thirty-minute server-side timer. Scores are saved as drafts continuously, so a
browser crash mid-evaluation loses nothing. On submit, the draft locks - the
code explicitly rejects further writes with "already submitted; draft locked" -
and the system issues a Secure Submission Receipt carrying a receipt ID. That
receipt is the evaluator's proof of what they submitted and when, which matters
when marks are later disputed.

Missed Submissions catches evaluations that were started but never completed.


-------------------------------------------------------------------------------
6. THREE PIECES OF ENGINEERING WORTH A CLOSER LOOK                  (3 minutes)
-------------------------------------------------------------------------------

[Pick these deliberately - they show depth beyond CRUD.]

THE MENTOR ALLOCATION ENGINE

Matching sixty teams to twenty mentors by hand is a day's work and produces a
bad answer. So it's automated - and notably, WITHOUT AI.

It's a deterministic weighted scorer: domain match forty percent, keyword
overlap thirty percent, mentor experience ten percent, and availability twenty
percent.

Domain matching is the clever part. It doesn't compare strings - it uses a
domain taxonomy that clusters related terms, so a team tagged "computer vision"
matches a mentor who listed "deep learning", because both sit in the same
cluster. Keyword overlap is set intersection between the team's required skills
and the mentor's declared expertise. Availability is current team count against
their declared maximum, so the algorithm naturally load-balances.

The engine's own docstring explains why embeddings were left out: the deployment
has no reliable AI key, so an embedding-based engine would silently collapse to
rule-only anyway. Rather than ship something that degrades invisibly, it commits
to the rule engine - which is fully functional, self-contained, and, importantly,
EXPLAINABLE. Every recommendation comes back with a score breakdown and a
human-readable reason. A coordinator overriding the machine can see exactly what
the machine was thinking.

THE AGENT MODULES

The admin service hosts four background modules: a communication agent for
segmented mail merge, an analysis agent for aggregate reporting, a notification
agent, and a deadline scheduler.

Alongside those run genuine background schedulers - a presentation reminder
service that fires email and Twilio calls ahead of slots, a GitHub sync
scheduler that pulls repository activity on a cycle, and a communication
scheduler for queued sends.

SECURITY HARDENING

I want to be candid about this because it's recent and substantial work.

A full security review of the platform found thirteen vulnerabilities, and all
thirteen are now fixed. The most serious: the admin API had no authentication at
all - every endpoint was reachable unauthenticated, and because it used a
service-role database key, Postgres RLS gave no protection. That's now closed
with an application-level guard rather than per-route decorators, specifically so
a future forgotten decorator can't reopen it.

Also fixed: privilege escalation where a mentor's token satisfied admin-only
routes; an account-claiming flaw in student signup; stored XSS through the mail
merge; javascript: URLs reaching admin document viewers; and SSRF in the
repository checker, where a "github dot com" substring test left the host
attacker-controlled.

And live production credentials had been committed to the deployment workflow -
those are now pulled from GitHub secrets, with rotation as a follow-up action.

The lesson I'd draw: none of these were exotic. They were ordinary gaps that
appear when a system grows fast across four services. Which is the argument for
reviewing the whole surface, not just the code you changed last.


-------------------------------------------------------------------------------
7. CLOSE                                                           (45 seconds)
-------------------------------------------------------------------------------

[Land it. Don't rush.]

So - to bring it back together. Four portals, four services, 313 endpoints, one
shared Postgres schema of 25-plus tables, containerised and continuously
deployed.

But the number I'd actually leave you with isn't any of those. It's this: the
platform takes a process that used to run on spreadsheets and email threads -
team formation, project allocation, mentor matching, scheduled evaluation, and
grading - and gives every one of those steps an audit trail, a deadline, and a
defined owner.

The engineering is in service of that. Thank you - happy to take questions.

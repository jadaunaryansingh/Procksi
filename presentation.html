Architecture / the whole system

One lifecycle, four portals, three gates

Stage, not just role

A coordinator is still a coordinator after grading closes, but the freeze gate has changed what that means. The same request is legal in one stage and rejected in the next.

Agents advise, people decide

Allocation, risk and quality signals arrive as recommendations with a visible reason. Approving, assigning, finalising and publishing stay with a person.

Unlocking is an event

An override is not a quiet exception. Reopening a frozen stage is a recorded action with an actor, a timestamp and a justification behind it.

Design rationale

Why four services, not one monolith

01 / Blast radius

Unequal trust

Students are the largest and least-trusted population; panel members need a narrow slice for two hours. A flaw in the student API cannot reach admin functionality. That code isn't loaded in that process.

02 / Load shape

Different lifecycles

Panel is idle for weeks, then serves every evaluator at once on presentation day. Student API peaks during team formation. Separate processes scale and restart independently.

03 / Identity

Two auth models

Admin authenticates through Supabase Auth. Student, mentor and panel mint their own HS256 JWTs with refresh rotation and a revocation blacklist. Cleaner apart than tangled together.

Architecture / request lifecycle

Two ways a request proves who it is

The admin service delegates identity to Supabase Auth. The other three verify a token they minted themselves, then check it against the revocation blacklist, which is what makes logout actually revoke.

Row Level Security is enabled at the Postgres level beneath the application's own checks. The schema evolves through numbered SQL migrations, each carrying a comment explaining the failure it fixes. The schema documents its own history.

Data / the keystone

semester_id carries the whole system

Almost every table carries this column. It is what lets third-year and fourth-year cohorts occupy the same tables concurrently without contaminating each other.

What it enables
  • Two cohorts running different phases simultaneously
  • Historical semesters kept intact and queryable
  • A global filter that scopes every screen to one batch
  • Server-side scoping: the API filters before data leaves the database
Master data

The students table is the authoritative roster. Nothing else creates a student. Signup validates against it, and every authenticated request re-checks that the token's email still resolves to a row. Remove someone from master data and their sessions stop working.

Data / master data

One spreadsheet becomes three tables

Column headers are resolved through an alias table: E-mail, Email ID and Mail all land in one field, because sheets never arrive in a fixed shape.

Data / the single source of truth

Master data: one roster the platform trusts

A student comes into existence in exactly one place, and the platform reads that one table as its answer to a single question: is this a real student in this cohort?

The roll number is the key

students.id is the university roll number, so every write is an upsert on that column. Re-importing last week's sheet corrects rows instead of doubling them.

One edit, three tables

A name corrected on the master record is rewritten into the teams_validation JSONB array and the unassigned_students row, so the copies cannot drift.

Cohort-scoped on write

The active semester_id is applied by the write layer rather than trusted from the caller, so two batches share one table without seeing each other.

Engineering / evaluation integrity

A one-way transition, on the clock

Engineering / 01

Mentor allocation: deliberately not AI

Matching sixty teams to twenty mentors by hand is a day's work and a bad answer. This is a deterministic weighted scorer.

Domain match40%
Keyword overlap30%
Availability20%
Experience10%
Domain taxonomy

Related terms are clustered, so semantically-adjacent expertise still scores as a match.

Load balancing

Availability is current teams against declared maximum, so the algorithm distributes naturally.

Explainability

Every recommendation returns a score breakdown and a human-readable reason. A coordinator overriding it can see what it was thinking.

Why no embeddings? Without a reliable AI key an embedding engine collapses to rule-only silently. Better to commit to the rule engine than ship something that degrades invisibly.

Engineering / 03

Security review: 13 findings, all closed

Critical
  • Admin API had no authentication: every endpoint reachable unauthenticated, and a service-role key meant RLS gave no protection
  • Unauthenticated creation and deletion of administrators
  • Live production credentials committed to the deploy workflow
High
  • Mentor tokens satisfied admin-only routes
  • Signup could claim an un-onboarded classmate's account
  • Stored XSS through the mail merge
  • Reset tokens signed with a leaked key
Medium
  • SSRF: a "github.com" substring test left the host attacker-controlled
  • Any member could remove any teammate
  • Logout did not revoke tokens

The admin fix registers the guard on the application, not per route, so a future forgotten decorator cannot reopen the hole. None of these were exotic; they are the ordinary gaps that appear when a system grows fast across four services.

Close

What the platform actually changed

A process that ran on spreadsheets and email threads (team formation, project allocation, mentor matching, scheduled evaluation, grading) now gives every one of those steps an audit trail, a deadline, and a defined owner.
